# Data inventory

Every piece of data Edge holds, where it lives, why it exists, and how it leaves. This is the
source of truth behind `/legal/privacy` — if the two disagree, this file is right and the page
needs updating.

Generated by reading `edge/api/store.py`. Re-read it whenever the schema changes.

---

## 1. What we store

All of it is in one SQLite file (`EDGE_DB`, default `.cache/edge.db`), nine tables. A Postgres
twin (`edge/api/store_pg.py`) holds the same nine when `DATABASE_URL` is set, and
`tests/test_store_contract.py` runs one suite against both so they cannot drift.

### `users` — the account
| Field | Example | Why |
|---|---|---|
| `email` | `andrew@example.com` | The account, and the key every other table hangs off |
| `password_hash` | `scrypt$16384$8$1$<salt>$<hash>` | A salted scrypt hash. The password itself is never stored and cannot be recovered from this |
| `name` | `Andrew` | Optional, what they typed at registration |
| `role` | `user` / `admin` | Who may open the front office. `EDGE_ADMINS` is the other way in |
| `created`, `last_login` | unix ts | — |
| `phone` | `+15552345678` | E.164, unique. Set when someone signs up or signs in with their phone, or adds one on `/account`. Only ever texted a sign-in code, through Twilio Verify |

A phone-only account has no address, so its key is `p15552345678@phone.invalid` (a reserved
domain that can never receive mail); adding an email moves every row onto the real address
(`rekey`). Its `password_hash` is empty: it signs in by texted code.

Personal data: **email, an optional name, a password hash, and an optional mobile number.** The hash is never exported
(`HIDDEN_COLUMNS`) and never leaves the store.

### `sessions` and `resets` — signed-in devices, and pending password resets
| Field | Why |
|---|---|
| `token_hash` | SHA-256 of the bearer token the browser holds. The token itself is never stored, so a copy of the database signs nobody in |
| `email` | Whose |
| `created`, `expires` | Sessions last 30 days; reset links two hours |
| `used` (resets only) | A reset link is spent once |

Sign-out deletes the session row; a password reset deletes every session for the account.

### `phone_tickets` — a verified number finishing sign-up
Same shape as `resets`, keyed by `phone` instead of `email`: a SHA-256 token hash, 30 minutes,
spent once. Pruned on every sign-in. The texted code itself is Twilio's and never stored here.

### `purchases` — what someone bought
| Field | Example | Why |
|---|---|---|
| `email` | `andrew@example.com` | The key an entitlement hangs off |
| `sku` | `full_report` | Which pass |
| `season` | `2026` | Passes are season-scoped |
| `source` | `stripe` | Distinguishes real sales from comps and tests |
| `ref` | Stripe session id | Reconciliation and refunds |
| `created` | unix ts | — |

Personal data: **email only.** No card details, no name, no address. Stripe holds those.

### `leagues` — which leagues an account connected
| Field | Example | Why |
|---|---|---|
| `email` | `andrew@example.com` | Owner |
| `platform` | `sleeper` | — |
| `league_id` | `1403186749361901568` | Public identifier on the platform |
| `team_id` | `3` | Which roster is theirs |
| `name` | `The Megalabowl` | Display |
| `team_name` | `HusH` | Display, so a returning account lands without a lookup |
| `created`, `last_used` | unix ts | Which league to open on the next sign-in |

Up to three per account, more with a `league_slot` purchase, five with the bundle
(`edge/products.py`). Linking one requires an account since 2026-09-24.

League ids and names are public on Sleeper and ESPN. The sensitive part is the *link* between an
email and a league, which is what deletion breaks.

### `email_prefs` — who asked for the weekly email
| Field | Example | Why |
|---|---|---|
| `email` | `andrew@example.com` | Who asked |
| `opt_in` | `1` | `1` yes, `0` no — one row per account, rewritten when they tick or untick |
| `created`, `updated` | unix ts | When they first chose, and when they last changed it |

Personal data: **email only**, plus a yes or a no. Written **only** when a signed-in user ticks
or unticks the box on `/login`; nothing else creates a row. An address with no row is not opted
in, so the absence of a record can never be read as consent, and `edge/delivery/send.recipients`
starts from this table rather than from "everyone who connected a league".

An untick writes `opt_in=0` rather than deleting the row, because the record of having been asked
and having said no is worth keeping: it is the difference between "never subscribed" and
"unsubscribed", and a deleted row would let a later bug quietly re-add them.

There is no Resend key and no verified sending domain today, so nothing on this list has ever been
sent anything. `edge/delivery/send.py` refuses to send without `EDGE_EMAIL_PROVIDER=resend`,
`RESEND_API_KEY` and `EDGE_EMAIL_FROM`, and the CLI wants `--send` on top of that.

### `runs` — what we recommended
| Field | Why |
|---|---|
| `email`, `platform`, `league_id`, `team_id`, `week` | Who we said it to |
| `kind` | `actions`, `waiver_plan`, `trade_finder`, `report` |
| `algo_version` | Which version of the engine produced it |
| `payload` | The full recommendation, JSON, capped at 200 KB |
| `created` | unix ts |

This is the learning loop and the substantiation for every accuracy claim we make. It is also the
largest store of personal data we have, because the payload contains a user's full roster.
Retention is therefore a real decision, not a formality — see §4.

Written on every feed, waiver plan, trade-finder and report request, including for signed-out
users, where `email` is the empty string.

### `feedback` — Helpful / Wrong votes
| Field | Why |
|---|---|
| `email`, `platform`, `league_id`, `team_id`, `week` | Whose vote |
| `action_id`, `action_type` | Which recommendation |
| `verdict` | `helpful` or `wrong` |
| `reason` | One of five canned reasons, or null |
| `created` | unix ts |

Free-text is not accepted, so a user cannot accidentally put something sensitive here.

### `shares` — public verdict snapshots
| Field | Why |
|---|---|
| `id` | 8 chars, unguessable, no look-alike characters |
| `payload` | Display fields only |
| `created`, `views` | Measuring the growth loop |

**No email. No league id. No roster beyond the players in the deal.** Enforced by
`edge/api/share.py` and asserted by `tests/test_share.py`. This is why a deletion request does
not touch this table: there is nothing in it belonging to anyone.

## 2. What we deliberately do not store

- Passwords in the clear, or session tokens in the clear. Only salted scrypt hashes and SHA-256 token hashes.
- Card numbers, billing addresses, anything payment-adjacent. Stripe's problem, on purpose.
- IP addresses, device identifiers, advertising identifiers, cross-site tracking.
- League chat, message content, or anything social from the platform.
- Anything at all for a signed-out visitor who connects a league. That choice lives in their own
  browser (`web/src/lib/storage.ts`) and never reaches us, apart from an anonymous `runs` row.

## 3. Where it goes

| Recipient | What they get | Why |
|---|---|---|
| **Sleeper** | A request for a public league, players, projections, transactions | It is the user's league |
| **ESPN** | Same, for public leagues | Same |
| **Stripe** | Email, amount, SKU | Taking the payment |
| **Supabase** (optional) | The whole store, when `DATABASE_URL` points at its Postgres | Hosting the database. It no longer handles sign-in |
| **Anthropic (Claude API)** | Player names, the engine's numbers, the other manager's tendency summary | Writing the trade explanation |
| **Resend** (planned, not live) | Email address, the rendered weekly email | Delivery. No key and no verified sending domain yet, so nothing has been sent |
| **Vercel / API host** | Whatever transits the request | Running the servers |
| **Analytics** (planned) | Page views and six named events, no personal identifiers | Knowing which channel works |

**The Claude API request is worth being precise about**, because it is the one users will ask
about. `edge/engine/explain.py:verdict_payload` sends the verdict, both sides' value and lineup
deltas, the fairness score, the other manager's tendency summary, the counteroffer, and player
names. It does **not** send an email address, a league id, a team id, or a full roster. The
privacy page says exactly this, and it is checkable against the code.

Nothing is sold. Nothing is shared for advertising. There is no data broker in this list.

## 4. Retention

| Data | Kept | Then |
|---|---|---|
| `purchases` | Life of the account | Deleted with the account |
| `leagues` | Life of the account | Deleted with the account |
| `email_prefs` | Life of the account | Deleted with the account |
| `runs` | Through the following season | Deleted — **needs a job, does not exist yet** |
| `feedback` | Through the following season | Deleted — **needs a job, does not exist yet** |
| `shares` | Indefinitely | Deleted on request |

The two gaps are real. The privacy page promises a retention limit on `runs` and `feedback` and
nothing enforces it today. That is a half-day job: a scheduled delete of rows older than one
season. Until it exists, the promise is a promise we intend to keep rather than one we do keep,
and it belongs on the open list.

## 5. Access requests

Both are shipped and tested:

```
GET    /api/me/data              # everything we hold, as JSON
DELETE /api/me?confirm=delete    # erase it
```

Deletion removes rows from `purchases`, `leagues`, `runs`, `feedback` and `email_prefs`, and returns
a count per table so the caller can see what happened. `email_prefs` is in that list deliberately: a
preference that outlived a deletion request is how someone gets email after asking to be forgotten,
and `tests/test_store_contract.py::test_deleting_an_account_unsubscribes_it` pins it on both
backends. It intentionally does **not**:

- Touch `shares`, which hold nothing of theirs and which other people may have links to.
- Preserve entitlements. Deleting the purchase row revokes the season pass. That is the honest
  consequence and both the API docstring and the privacy page say so before it happens.

The `confirm=delete` query parameter exists so a mis-routed request or an over-eager client cannot
erase an account by accident.

**Not yet wired:** a button in the UI. Today this is an API call or an email to support. For the
volume we expect this season, an email to a human is an acceptable answer, and it is what the
privacy page offers.

## 6. Breach plan

Small surface, but write it down before it is needed:

1. The credentials worth stealing are the Stripe secret key, the database connection string and the
   Anthropic API key. All are environment variables on the API host, none are in the repo.
2. If the host is compromised, assume the SQLite file is gone: emails, league ids, rosters,
   recommendation history and who asked for the weekly email. No passwords and no card data, which is the point of not holding them.
3. Rotate all three keys, delete every row in `sessions` (signs everyone out), restore purchases from Stripe (the source of
   truth), and email every address in the file with what happened and when.
4. Nothing here is medical, financial or otherwise special-category data, so the disclosure duty
   is ordinary. Being prompt matters more than being lawyered.
